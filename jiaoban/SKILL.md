# 交班

会话是随时可以换掉的员工。上下文要短，记忆要放在会话外面，跟着 git 提交走。下一个会话只读一份交接，就能接着干。

## 为什么可以这样

NVIDIA 的论文《You don't need long context》（arXiv 2611.05306，2026-11-03）在 13 个基准上测了 Claude Opus 4.5 和 GPT 5.6 Sol：

- **长程任务**（SWE-bench Verified、Terminal-Bench 2.1 等 6 个）：上下文一满就压成一份状态，再开新对话，正确率和一直不压比，Opus 在 −3.7 到 +5.6 分之间，GPT 在 −3.3 到 +4.4 分之间。每个模型 22 组设置里，掉分超过 2 分的不到 5 组。
- **长输入任务**（LongBench v2、NIAH 等 7 个）：把材料放成文件、按需去读，比一次全塞进上下文更准。Opus 在 −0.4 到 +40.0 分之间，GPT 在 +1.0 到 +30.9 分之间。
- **每步一换**：每个对话只做一个动作就丢掉，只带一份状态往下传。Opus 在 SWE-bench Verified 上 70.0 到 70.2，没掉；GPT 掉了 2.0 分。
- **长上下文更贵**：同样的显卡，上下文窗口从 16K 开到 256K，每个输出 token 贵 3.6 到 7 倍（GLM 5.2、Kimi K2.6、Qwen 3 Coder Next 实测）。

所以长上下文不是必需的。好的交接，加上按需翻原始记录，就够了。数字和出处见 `references/paper.md`。

## 选哪种方式

| 方式 | 怎么做 | 论文结果 | 用不用 |
|---|---|---|---|
| FHA（全量累积） | 什么都不删，记录一直往上堆 | 基线 | 不用。长、慢、贵 |
| **EoCC（到阈值压一次）** | 上下文到阈值（约总上限的四分之三）就写一份状态，开新对话，带上原任务和状态接着干 | 四组主实验全是最高分：Opus SWE-bench Verified 74.8，GPT 88.8 | **默认用这个** |
| SAC（每步一换） | 每个对话只做一个动作，做完就丢，只传状态 | 和基线持平或略低，GPT 掉 2.0 到 3.3 分 | 不用。正确率不更高，论文也没给出它的 token 花费 |

落到会话上：一个会话做一件事，做完或者会话变长了就写交接、换新会话。不必每做一步就换人。

## 开工

1. 跑 `jiaoban brief`，读现状卡：进行中的事、最近的决定、最近三份交接、项目自检。领了岗位加 `--role <工号>`。
2. 要细节时按需去翻：`grep`、`sed -n` 看一段、`git show` 看一次提交、打开某一份旧交接。不把整份长文件、整段历史读进来。论文里按需读比整份塞进去更准，见上面的长输入任务。
3. 接事前跑 `jiaoban open <工号> <事>`，事只用小写英文、数字和横线。
4. 一个会话只做一件小事。

## 干活中

- 命令输出要窄：用 `head`、`tail`、`grep` 截出要看的部分。论文里 Qwen 3 Coder Next 输出太啰嗦，两次压缩之间干不了多少活，SWE-bench Verified 从 53.0 掉到 3.6。
- 会话被自动压缩过一次，或者已经很长，先按下面的格式写一份交接，再接着做或者换新会话。自动压缩是通用摘要，不一定带上任务原文和完成标准。
- 交接要留出余量写，不要等上下文快满了才写。论文给写状态留了专门的余量（阈值约为总上限的四分之三），没写完就判失败。

## 收工：写交接

交接写在 `memory/handoff/<日期>-<工号>-<事>.md`，开头是 YAML front matter，一个字段一行。

**交接是写给下一个人的简报，不是这一段的流水账。** 论文附录 A 发现，最能保住正确率的压缩不是忠实复述经过，而是挑出接着干要用的事实。普通摘要会把重复出现的片段看得太重。

| 字段 | 必填 | 写什么 | 论文依据 |
|---|---|---|---|
| 工号 | 是 | 谁做的 | |
| 事 | 是 | 事的短名 | |
| 任务原文 | 是 | 派活方的原话，照抄，不改写 | 附录 A 第 1 条：带上原样的任务。§3.1：压缩的压缩丢得更多，所以原话每次照抄，不转述转述 |
| 结论 | 是 | 做到哪了，最好的结果是什么；验证过的和猜的分开写 | 附录 G：把观察到的和没验证的想法分开 |
| 改了哪些文件 | 是 | 每个改过或新建的文件，用 `[a, b]` 写 | 附录 G：改动清单，各自验证没有 |
| 怎么验的 | 是 | 跑了哪些检查，结果是什么 | 附录 G：验证 |
| 走不通的 | 是 | 试过不行的路，别再走；没有就写「无」 | 附录 G：死路，不要重复 |
| 没做完的 | 是 | 还剩哪些 | 附录 A 第 2 条：当前在做什么、打算做什么 |
| 下一步 | 是 | 下一个人要做的第一条具体命令或改动 | 附录 G：紧接着的那条命令或改动 |
| 完成标准 | 是 | 什么时候算做完 | 附录 A 第 3b 条：完成条件 |
| 肥肥交代的 | 否 | 这次用户说过的偏好和纠正 | 附录 A：有人在环路里时，要保住人的反馈 |
| 去哪查 | 否 | 关键事实的位置：`文件:行`、提交号、一条窄命令 | §3.1：原始记录按需取回；附录 G：输出被截断就给一条窄命令去取 |

写完：

1. 把改过的文件提交进 git。
2. 跑 `jiaoban close <工号> <事>`。它检查必填字段齐全、列出的文件已提交、项目的收工检查通过，然后把这件事标成做完。不通过就是没交接完。

好的交接和流水账的差别：

```
流水账：先看了 config，发现路径不对，试了相对路径不行，又试了绝对路径，然后跑测试……
简报：  结论: 路径改成从仓库根算的绝对路径，测试 41 个全过（已验证）
        走不通的: 相对路径，换工作目录就断
        下一步: 跑 make deploy
```

## 交接有损，原始记录要留着

压缩一定会丢信息。论文的解法是把每条原始记录都留着，需要时按需去翻。所以：

- git 提交、会话记录、日志、数据都不删。
- 交接里写指针（文件、行号、提交号、命令），不抄全文。
- 接手的人觉得交接对不上时，回原始记录核对，不要凭印象补。

## 离职

会话要被归档前跑 `jiaoban resign`。没提交的改动自动保全到 `refs/keep/auto/<分支>`；HEAD 没推到远程，就留本地保全分支 `keep/<分支>-<日期>`。今天没写交接，或者还有该进项目的改动，就不通过。确定只留保全的加 `--keep-dirty`。一个仓库的所有工作树一起保全用 `jiaoban sweep --dir <仓库>`。

## 派活给子代理或别的模型

任务书就是一份交接：任务原文、完成标准、能改哪些文件、怎么验。

模型越弱，越不能压得太紧。论文里 Step 3.7 Flash 和 Opus 4.5 不压缩时 SWE-bench Verified 都是 70.0；压到 16K 上限、12K 阈值时，Step 3.7 Flash 掉到 56.6，Opus 是 68.8。跑分高不等于经得起压缩。给 DeepSeek、Kimi、量化过的本地模型派活：

- 任务切小，一次一件。
- 要求输出要窄。
- 阈值放宽，不要压到很小。

## 工具

`jiaoban` 的源码在 `scripts/jiaoban.py`，只用 Python 标准库。

| 命令 | 做什么 |
|---|---|
| `jiaoban init` | 新项目建 `memory/decisions.md`、`memory/work.json`、`memory/handoff/`、`roles/`，把交班规则写进 CLAUDE.md 或 AGENTS.md |
| `jiaoban brief [--role <工号>]` | 打印现状卡 |
| `jiaoban open <工号> <事>` | 登记接事 |
| `jiaoban close <工号> <事>` | 检查交接，通过后标成做完、提交 memory/ |
| `jiaoban resign [--keep-dirty]` | 离职检查和保全 |
| `jiaoban sweep --dir <仓库>` | 保全仓库所有工作树 |
| `jiaoban snapshot` | 只拍一次保全快照 |

项目自己的自检命令写进 `memory/jiaoban.json` 的 `brief_extra`；收工必须过的检查（比如全部测试）写进 `close_check`。

## 哪些靠结构管住，哪些只靠提示词

| 规则 | 怎么管 |
|---|---|
| 必填字段齐全、改过的文件已提交、收工检查通过 | `jiaoban close` 检查，不过不让交班 |
| 离职前保全、今天有交接 | `jiaoban resign` 检查 |
| 会话变长先写交接 | 只靠提示词 |
| 交接写简报不写流水账、开工按需读 | 只靠提示词 |

## 局限

- 论文测的是 Opus 4.5 和 GPT 5.6 Sol 在基准上的单次任务，不是 Claude Code 里和人来回的长会话。结论能借，数字不能直接搬。
- 论文里 2.2 到 8.8 倍的省钱，是假设按上下文长度定价的估算。按今天统一的标价，压缩不一定省钱：SWE-bench Verified 上 Opus 便宜约 10% 到 30%，GPT 贵约 10% 到 21%。
- 论文没给每步一换的 token 花费。
- 论文没测 DeepSeek。
- 论文自己说没有排除确实需要长上下文的任务。
